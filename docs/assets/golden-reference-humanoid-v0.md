# Golden Reference Humanoid V0

## Purpose

`Superhero_Male_FullBody.gltf` is the first Golden Reference Humanoid for the
Adventure Game Builder and Asset Studio work. It validates the existing
registry, glTF loader/cache, material preparation, asset analysis,
`SkeletonUtils` cloning, shared Three renderer, editor preview, runtime
presentation, and diagnostics path. It is an engineering fixture, not a
production character-art choice or Asset Studio output.

## Measured Source Structure

Programmatic inspection of the unmodified glTF found:

- glTF 2.0, generated by Khronos glTF Blender I/O v4.3.47
- one scene rooted at `Armature`; 69 nodes total
- three skinned meshes: `Face`, `Face.001`, and `Sphere.005_Retopology.004`
- 8,483 vertices and 14,318 triangles
- one armature skin, 65 joints, and three material assignments
- seven external texture references and one external 720,076-byte buffer
- no morph targets and no embedded animation clips
- measured source-space bounds: X `-0.9294..0.9294`, Y `-0.0095..1.8101`, Z
  `-0.1635..0.1280`; approximate height 1.820 units

The mesh is Y-up and face geometry lies on native +Z. The registry applies a
180-degree Y rotation so its visible forward matches the engine's -Z forward.
The shared renderer grounds it from measured minimum Y before applying its
registry scale of 0.75 and zero height offset.

The skeleton is `root -> pelvis -> spine_01 -> spine_02 -> spine_03`, with
`neck_01`, `Head`, left/right clavicle-arm-hand chains, complete finger chains,
and left/right thigh-calf-foot-ball chains. Its 65 joint names are preserved
verbatim by the source asset; runtime diagnostics expose the loaded bone count.
It is intentionally a richer skeleton than the provisional `humanoid-v1`
minimal contract and is not evidence that the final Asset Studio contract is
ready to freeze.

## Resource Resolution

The source buffer and five texture URIs resolve as supplied. The source
references `T_Hair_1_Normal_png.png` and `T_Eye_Normal_png.png`, while the
included files are named `T_Hair_1_Normal.png` and `T_Eye_Normal.png`.

The registry owns two scoped aliases for these requests. The Three loader
applies them only for this definition through its loading manager. This keeps
the vendor directory unchanged, avoids a modified glTF copy, and lets all
referenced resources resolve in development and production static builds.

## Engine-Facing Configuration

The built-in definition id is
`golden-reference-quaternius-superhero-male`. It is a `character` `gltf`
registry entry with `standard` material preparation, cast shadows enabled,
receive shadows disabled, 0.75 default scale, zero height offset, and 180
degrees rotation offset. It deliberately has no animation mappings.

Player and NPC authoring both use the existing `ThreeVisualControls` character
asset selection and the shared `resolveThreeCharacterVisual` / renderer path.
No data model, gameplay state, or renderer-specific object is added to
`GameProject` or `RuntimeSession`.

## Runtime And Editor Status

The cache analyses the source once and creates an independent
`SkeletonUtils` clone for each player/NPC/editor instance. Geometry, materials,
and textures remain shared; skeletons and bones are instance-local. The shared
renderer applies normalisation, facing, grounding, and shadow metadata in both
the editor 3D view and experimental Three runtime.

No animation clips are embedded. The model is intentionally renderable in its
bind/rest pose. Diagnostics consequently show the loaded character asset and
metrics with `clips none`; no idle, walk, attack, or defeated mapping is
claimed. Animation retargeting is a subsequent milestone.

## Limits And Next Step

This fixture is within neither the preferred 12,000-triangle budget nor the
32-bone preference: it has 14,318 triangles, 65 bones, and three materials.
It is suitable as a Golden Reference for pipeline validation, but not yet as a
production crowd-budget default.

The smallest next task is an animation-retargeting feasibility spike against
this exact skeleton, beginning with a real idle and walk source and validating
track compatibility before adding any registry mappings.

## Boundary With Asset Studio

The Quaternius vendor model and the game registry definition are distinct from
future Asset Studio output. Asset Studio recipes remain editable source data;
future compiled GLB packages and metadata must be independently generated and
round-trip validated rather than being inferred from this fixture.
